# 业务过程优先的数仓建模

数仓分层是治理手段，不是建模起点。先回答“一行数据代表什么业务事实、谁会消费、需要保留什么历史”，再决定数据应停留在 ODS、进入 DWD、沉淀为 DIM、汇总到 DWS / DM，还是直接交付到 ADS。

不要根据层名反推职责，也不要把“多建一层”当作规范性本身。一个只复制字段、没有新增稳定语义或复用价值的 DWD，比消费者直接读取契约良好的 ODS 更难维护。

## Context

- 需要建设或评审分析型数据模型、数据集市、指标体系或报表数据。
- 团队使用 ODS、DWD、DIM、DWS / DM、ADS 等分层词汇，但对边界理解不一致。
- 同一来源数据可能被一个或多个消费者使用，需要决定是否建立共享明细契约。
- 需要处理 CDC、迟到数据、历史状态、维度变化、回刷、指标复用或消费隔离。

如果任务只是一次性数据导出，且没有长期复用、历史解释或稳定口径要求，不必先建设完整数仓分层。

## Problem

从“这张表应该放哪一层”开始讨论，容易出现两类相反错误：

- 机械分层：ODS、DWD、DWS、ADS 每层都复制一遍数据，但没有明确新增的契约、复用或隔离价值。
- 无边界直读：所有消费者直接依赖来源表，分别处理去重、事件时间、状态、敏感字段和业务口径，最终得到互相矛盾的结果。

层名也容易被误当作建模语义。例如，DWD 不是“专门做维度转换或行转列”的层；它的主要价值是形成稳定、可复用、保持原子粒度的业务事实契约。转换只是实现这个契约时可能发生的动作。

## Forces

- 来源忠实性与下游易用性存在张力：越接近来源越容易重放，越接近业务语义越容易稳定消费。
- 复用能减少重复治理，但共享层也会增加建设、回刷、血缘和变更成本。
- 实时与离线链路可以使用不同物理实现，但同一业务事实的粒度、主键和时间语义必须一致。
- 当前状态查询、历史追溯和事件分析需要不同的事实类型，不能用一张万能宽表全部承担。
- 指标可能是可加、半可加或不可加；错误聚合会产生看似合理但无法解释的数字。
- 分区、文件格式、引擎和调度是物理设计，不能替代业务建模。

## Pattern

按以下顺序设计，不从层名或表名开始：

```text
业务过程与决策问题
  → 声明粒度
  → 选择事实类型
  → 识别维度与历史策略
  → 定义主键、时间和质量契约
  → 判断共享与隔离价值
  → 选择需要的数仓层
  → 设计物理实现与验证
```

### 1. 先定义业务过程和问题

业务过程是可发生、可观察的动作或状态演进，例如“用户授权”“订单支付”“车辆交付”“账号每日活跃状态”。先列出消费者真正要回答的问题，再判断哪些事实需要长期保留。

以“用户授权审计”为例，问题可能包括：

- 哪个主体在什么时间给哪个用户授予或撤销了什么权限？
- 某组织每天发生多少次权限变更？
- 当前用户拥有哪些权限？
- 一次异常授权经过哪些审批和操作？

这四个问题不应天然落在同一张表：权限变更事件、每日汇总、当前状态和审计案件具有不同粒度。

### 2. 为每张事实表声明唯一粒度

用一句话写清“一行代表什么”，并让主键、去重键、维度外键和指标都服从这句话。

示例：

- `fct_user_permission_change`：一行代表一次已经生效的用户权限变更事件。
- `fct_order_item`：一行代表一个订单中的一个商品明细。
- `fct_account_daily_snapshot`：一行代表一个账号在一个自然日结束时的状态。
- `fct_delivery_process`：一行代表一辆车从下单到交付完成的一次流程实例。

不要在同一表中混合“事件明细”和“每日汇总”，也不要因为查询方便就把不同粒度的字段放进一张宽表。

### 3. 选择事实类型

- 事务事实：记录一次不可再分的业务事件。例如授权、支付、退款、登录。
- 周期快照事实：按固定周期记录状态。例如账号日末状态、库存日快照。
- 累计快照事实：用一行跟踪有明确里程碑的流程。例如下单、付款、出库、交付时间。
- 无事实事实表：记录某个关系或覆盖范围，即使没有数值指标。例如用户参加活动、账号命中策略。

同一业务过程可能同时需要事件事实和快照事实，但必须分表并分别声明粒度。

### 4. 识别维度与历史语义

维度提供分析上下文，例如用户、组织、权限、应用、渠道、地区和日期。先判断消费者需要“事件发生时的属性”还是“当前最新属性”，再选择历史策略：

- Type 1：直接覆盖，适合不需要历史解释的更正。
- Type 2：保留版本和有效区间，适合需要按事件发生时属性分析。
- 固定快照属性：把少量关键属性复制进事实，确保事实长期可解释。

不要默认所有维度都做 SCD2。只有历史变化会改变分析结论时，版本化才有价值。

### 5. 定义跨层不变量

无论使用什么技术栈，都明确：

- Grain：一行的业务含义。
- Business key：业务稳定标识。
- Event key / dedup key：同一事件如何识别。
- Event time：业务事件实际发生时间。
- Ingestion time：平台接收时间。
- Effective time：状态或规则开始生效的时间。
- Late-arriving policy：迟到数据如何补入、改写或重算。
- Delete / correction semantics：来源删除和业务更正如何传播。
- Metric additivity：指标能否跨时间、主体或其他维度直接求和。
- Rebuild boundary：从哪个来源可以完整重建，回刷影响哪些下游。

### 6. 只有产生稳定价值时才新增一层

新增一层至少应承担一种清晰价值：

- 隔离来源 schema 变化。
- 统一业务主键、事件、状态或时间语义。
- 提供多个消费者复用的清洗和治理。
- 统一敏感字段、质量规则或跨来源整合。
- 提供共享聚合、性能边界或消费 SLA。

如果新层只执行 `SELECT *`、字段改名或无消费者的预聚合，应先证明它降低了真实成本。

## Layer Examples

### ODS：忠实、可追溯、可重放的来源层

ODS 保存来源系统可解释的原始形态和采集元数据。可以做解码、格式解析、坏数据隔离等技术处理，但不要悄悄改写业务含义。

示例一：`ods_iam_user_audit_event`

- 一行代表来源库 `t_user_audit_event` 的一条 CDC 变化记录。
- 保存 `op_type`、`source_pk`、before / after、来源事务位置、采集时间和原始 payload。
- 用于重放、核对来源和重建下游。

示例二：`ods_order`

- 一行代表来源订单表的一条当前记录或 CDC envelope，具体取决于采集契约。
- 保留来源状态码、金额原值、来源更新时间和删除标记。
- 不在这一层把订单状态改造成团队自定义的“已履约”口径。

ODS 可以被直接消费，但应明确它是稳定契约而不只是“离来源最近”。如果它已经完成可靠去重、类型统一、事件时间、水位和敏感字段治理，且只有一个或少量消费者，再建 DWD 可能没有收益。

### DWD：稳定、可复用、保持原子粒度的业务事实层

DWD 把来源变化解释为统一的原子业务事实，隔离来源表结构、代码值和采集细节。它可以清洗、去重、标准化和跨来源整合，但不应主要承担报表聚合。

示例一：`dwd_user_permission_change_event`

- 一行代表一次已经生效的授权或撤权。
- 统一 `actor_id`、`target_user_id`、`permission_id`、`action`、`effective_at` 和 `event_id`。
- 把来源的多种状态码映射为稳定业务动作，处理 CDC 重复和迟到事件。
- 不按天统计次数，也不把“当前权限集合”塞进同一行。

示例二：`dwd_order_item`

- 一行代表一个订单商品明细。
- 统一订单、商品、用户、渠道和币种标识，保留原子金额与数量。
- 退款是独立事实或明确的更正语义，不把不同粒度的订单汇总直接覆盖到明细行。

需要 DWD 的典型信号：

- 多个消费者正在重复处理同一份 ODS。
- 来源 schema 变化不应直接影响下游。
- 需要统一业务主键、事件定义、状态、时间或敏感字段。
- 需要跨来源拼成一个业务事实。
- 需要共享质量契约和可重复回刷。

可以暂不建设 DWD 的典型条件：

- ODS 已经是可靠、稳定、治理完备的明细契约。
- 消费者少且边界清晰。
- 新 DWD 只会原样复制字段。
- 未来是否复用尚无证据，当前可以保留清晰的升级路径。

### DIM：一致性分析上下文

DIM 统一多个事实表共享的分析维度，并明确当前值与历史值的关系。

示例一：`dim_user`

- 业务键是 `user_id`，代理键用于关联具体历史版本。
- SCD2 字段包括 `valid_from`、`valid_to`、`is_current`。
- 当用户所属组织变化时，历史授权事件仍可关联事件发生时的组织。

示例二：`dim_permission`

- 统一权限编码、名称、资源类型、风险等级和所属应用。
- 如果权限名称更正不应改变历史分析，可以使用 Type 1；如果风险等级变化需要历史追溯，则保留版本。

示例三：`dim_date`

- 提供自然日、周、月、季度、工作日、节假日等一致日历语义。
- 不要让每个报表各自实现“业务周”和节假日判断。

不是所有枚举或字典都值得单独建维度。只有它承担复用、历史或一致性语义时，DIM 才有价值。

### DWS / DM：面向主题的共享汇总或数据集市

DWS / DM 围绕稳定主题和消费群体组织可复用数据。DWS 常承担共享主题汇总，DM 常承担某业务域或团队的数据集市；具体命名以组织规范为准，不要只凭缩写判断。

示例一：`dws_org_permission_change_day`

- 一行代表一个组织在一个自然日的权限变更汇总。
- 指标包括授权次数、撤权次数、受影响用户数、操作人数和高风险权限变更数。
- 明确去重口径、时区和迟到事件重算窗口。

示例二：`dws_user_login_day`

- 一行代表一个用户一天的登录行为汇总。
- 保存首次登录时间、最后登录时间、成功次数、失败次数和设备数。
- `device_count` 等去重指标不能在更高层无条件相加。

示例三：`dm_security_audit_case`

- 一行代表一个安全审计案件，整合权限变更、审批、告警和处理结果。
- 服务安全运营这一明确消费域，不假装是所有团队通用的原子事实。

只有多个查询反复使用同一汇总、性能成本需要隔离，或主题模型本身形成稳定契约时，才提前建设 DWS / DM。

### ADS：面向具体应用的交付层

ADS 为明确的报表、接口、模型或运营应用提供最终形态，可以按消费 SLA 做反范式、裁剪和预计算，但不应成为共享业务口径的唯一事实源。

示例一：`ads_security_dashboard_daily`

- 直接服务安全看板。
- 一行代表日期与展示组织的组合，包含看板卡片需要的最终指标和同比环比。
- 字段、刷新频率和保留周期跟随看板契约。

示例二：`ads_user_permission_export`

- 服务审计导出任务。
- 展开用户、组织、权限名称和当前状态，允许为导出便利做宽表。
- 共享的授权事实仍来自 DWD，维度口径仍来自 DIM。

示例三：`ads_risk_model_feature_hour`

- 一行代表一个用户在一个小时窗口内的模型特征。
- 特征计算窗口、版本和回溯策略属于模型消费契约，不反向污染共享 DWD。

当 ADS 被多个无关消费者长期复用时，应重新判断其中是否有内容应上移为 DWS / DM 或共享指标语义。

## Layer Lineage

分层不是每一层都从 ODS 重新清洗，也不是必须逐层经过的固定流水线。默认让共享治理发生一次，再由下游复用已经稳定的事实和维度契约：

```text
业务源 ──→ ODS ──→ DWD ──┬──→ DWS ──┐
                          ├──→ DM  ──┼──→ ADS
                          └──────────┘
主数据 / ODS ──→ DIM ───────→ DWS / DM / ADS
```

这张图表达逻辑依赖，不要求每个项目物理建设所有层：

- ODS 从业务源采集，负责来源忠实、采集可追溯和可重放。
- DWD 通常从 ODS 解释出原子业务事实，统一去重、业务键、状态、时间和敏感字段等共享语义。
- DIM 可从主数据、ODS 或其他权威来源独立建设，为 DWD、DWS、DM 和 ADS 提供一致分析上下文；它不必被视为 ODS 到 DWD 之后的下一层。
- DWS 通常基于 DWD 和 DIM 建共享主题汇总，不应重新从 ODS 实现一遍同样的业务清洗。
- DM 可直接组合 DWD 与 DIM，也可复用已有 DWS；是否经过 DWS 取决于主题汇总能否复用，不固定要求 `DWS → DM`。
- ADS 优先消费 DWS 或 DM；需要事件明细、导出或明细接口时，也可直接消费 DWD 与 DIM。

同一项共享治理应有唯一 owner，并在最靠近其稳定语义的层完成一次。例如 CDC 去重和“授权生效事件”的解释属于 DWD 后，DWS、DM 和 ADS 应复用这个结果，只补充本层的聚合、主题整合或交付逻辑。若多个下游都从 ODS 重复实现同一规则，说明该规则应上移到共享 DWD；若 DWD 只是复制一个已经治理完备且消费者很少的 ODS，则允许直读 ODS，不为层级完整而复制。

## ODS or DWD Decision

用以下顺序判断，不直接问“规范要求哪一层”：

```text
ODS 是否忠实、可重放、质量可解释？
  ├─ 否 → 先修复 ODS 契约
  └─ 是
      ↓
是否需要稳定、可复用的原子业务事实？
  ├─ 是 → 建 DWD，并写清新增语义
  └─ 否
      ↓
消费者是否少、来源是否稳定、治理是否已完成？
  ├─ 是 → 可以直接消费 ODS，保留升级条件
  └─ 否 → 建 DWD 隔离变化和重复治理
```

以 `t_user_audit_event` 为例：

- 如果 ODS 已可靠去重、统一类型、提供事件时间和水位，只有一个审计处理消费者，而且 DWD 只会复制字段，则消费者直读 ODS 是合理选择。
- 如果多个审计、风控和报表消费者都需要统一“授权生效事件”，或者来源状态码、主体标识和时间语义不稳定，则建立 `dwd_user_permission_change_event`。
- 如果后续需要按组织和日期汇总，再从 DWD 建 `dws_org_permission_change_day`；不要把聚合职责塞回 DWD。

## Metric Semantics

定义指标时至少说明：

- 计算对象和过滤条件。
- 分子、分母和去重键。
- 时间字段、时区和窗口。
- 是否可跨时间、主体或维度直接相加。
- 迟到数据和更正是否触发重算。
- 指标 owner 和唯一权威实现。

示例：

- `permission_change_count` 是事务次数，可按组织和日期相加。
- `affected_user_count` 是去重用户数，不能把多个日期或组织的结果无条件相加。
- `account_balance` 是时点值，可按账号相加，但通常不能跨日期相加。
- `conversion_rate` 是比率，必须聚合分子和分母后重新计算。

## Failure Modes

- 先决定“必须上 DWD”，再寻找理由，最终只生成一张 ODS 镜像表。
- 把 DWD 定义成“维度转换、行转列或每天一张快照”，忽略原子事实契约。
- 一张表混合事件、当前状态和每日汇总，无法声明唯一粒度。
- 多个报表分别实现同名指标，过滤条件、时区或去重键不一致。
- 用万能大宽表承载所有历史和消费场景，字段语义随需求不断漂移。
- DIM 无差别使用 SCD2，产生大量无分析价值的版本。
- DWS 预聚合没有已知消费者，回刷和迟到数据成本高于查询收益。
- ADS 反向成为共享事实源，应用字段变更影响所有消费者。
- 只讨论 `di`、`df`、分区和文件格式，却没有定义粒度、业务键和时间语义。
- 认为层数越多治理越成熟，忽略每层的 owner、SLA、质量和重建成本。

## Implementation Checklist

- 写出业务过程、消费者和需要回答的决策问题。
- 为每张事实表写一句唯一粒度声明。
- 选择事务事实、周期快照、累计快照或无事实事实表。
- 定义业务键、事件键、去重键和维度关联方式。
- 区分 event time、ingestion time 和 effective time。
- 明确迟到、删除、更正、回刷和重建边界。
- 为维度选择 Type 1、Type 2 或事实快照属性，并说明历史需求。
- 为每个指标声明可加性、时区、窗口、去重和 owner。
- 为每一层写出它新增的稳定价值；无法写出时考虑删除该层。
- 记录当前允许 ODS 直读的条件，以及触发升级到 DWD 的信号。
- 设计血缘、质量检查、数据量对账、SLA 和失败恢复。
- 最后再决定分区、存储格式、引擎、调度和物化策略。

## Verification

- 随机抽取业务事件，从来源追踪到 ODS、DWD、汇总和 ADS，验证语义没有漂移。
- 对同一事件重复采集，验证 ODS 和 DWD 的去重契约。
- 注入迟到事件和业务更正，验证受影响层按声明回刷或重算。
- 变更来源字段或状态码，验证 DWD 消费者不需要同步理解来源细节。
- 用不同维度路径重算共享指标，验证口径一致。
- 对可加、半可加和不可加指标执行跨日期聚合，确认系统拒绝或正确重算错误用法。
- 回放一个完整时间窗口，验证结果可重复且能与来源对账。
- 删除一个没有新增价值的候选层，验证数据质量、复用和消费 SLA 是否真的受影响。
