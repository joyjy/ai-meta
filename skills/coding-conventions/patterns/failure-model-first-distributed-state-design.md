# 故障模型优先的分布式状态设计

分布式状态设计先明确必须守住的事实和允许保留的故障后果，再选择机制。角色含义、一致性措辞或单写边缘拓扑已成为主要疑问时，直接使用对应的更窄 pattern。

## Context

- 一项能力跨越进程、节点、区域、数据库或消息系统，局部成功不再等于整体成功。
- 团队正在比较 consensus、atomic commit、multi-primary、CRDT、Saga 或异步投影。
- 安全性、可用性、恢复时限与维护成本之间存在具体取舍。

如果状态能留在一个可靠事务边界内，优先保留单机设计。

## Problem

从 Raft、2PC、消息队列或数据库产品名出发，会把机制外形误当成问题定义。相似的复制拓扑可能拥有不同提交语义，timeout 也不能证明远端没有执行。

发现故障窗口，不等于业务要求自动恢复。先区分不可接受的数据错误与可发现、影响有界、修复成本可接受的残留。不能仅凭理论故障增加常驻任务或完整恢复协议。

## Forces

- **不可接受的后果**：越权、丢数据、重复占用或其他会破坏业务约束的结果。
- **可接受的残留**：允许哪些操作暂时停留在中间状态，能否发现并修复。
- **恢复要求**：是否必须无人介入、限定时间内完成，有什么实际依据。
- **总成本**：实现、运行、告警、维护与人工修复的成本，以及恢复动作自身的风险。

## Pattern

### 1. 声明状态边界与不变量

列出权威事实、派生状态及跨边界不变量。区分“不能做错”与“必须在何时完成”。没有恢复时限依据时标为未知，不自动补成持续自动恢复要求。

### 2. 选择满足要求的最简单路径

- 单一事务边界和现有约束足够时，停止扩展。
- 影响有界、可发现且修复成本可接受时，优先采用简单同步流程和现有查询、补做入口。
- 只有恢复时限、实际故障证据或安全与数据完整性要求需要时，增加自动恢复。
- 修复也先复用已有能力，有真实重复需求再建设专用工具。

### 3. 限定当前故障范围

沿当前变更的真实流程，说明故障后果、发现方式和修复路径。优先覆盖主路径和最大真实风险。仅在承诺对应能力时，展开网络分区、旧 owner、时钟或版本混跑场景，不默认穷举故障组合。

没有发生率数据时保留未知。低频不等于可忽略，后果严重且修复不可行时仍须保护；理论上可能发生也不等于需要新增机制。

### 4. 让机制回指约束

- 单一事务边界足够时使用本地事务和明确 owner。
- 需要副本对命令顺序达成一致并由多数派推进时评估 quorum consensus。
- 多个事务参与者必须共同提交或放弃时评估 atomic commit，并接受其阻塞与恢复成本。
- 分区两侧都必须提交时，证明状态可合并或指定冲突裁决；异步 projection 只传播已提交事实。

只分析所选机制依赖的前提。使用 timeout、lease 或 quorum 时，明确必要的延迟、时钟、持久化和故障域假设。基础设施不满足前提时，收缩承诺或重新选型。

### 5. 验证所承诺的恢复能力

人工修复方案验证可发现、可查询权威事实、可执行补做并回读结果。自动恢复方案验证实际故障窗口和承诺的恢复时限。只验证已采用的 snapshot、checkpoint、fencing、handoff 或重放机制，不为凑齐演练项目新增机制。

## Failure Modes

- 先选技术，再反推它能解决全部状态问题。
- 只写“高可用”或“最终一致”，没有故障域、收敛条件和恢复 owner。
- 把 timeout、心跳丢失或 lease 过期解释为远端已停止或请求未提交。
- 按实例数量计算冗余，忽略共享依赖和同批发布。
- 用物理时间戳决定跨节点顺序，却没有时钟与冲突契约。
- 把所有中间状态都视为必须自动消除的错误，忽略人工修复方案。
- 承诺某类故障下仍能恢复，却没有匹配的验证证据。

## Implementation Checklist

- 列出权威事实、派生状态和跨边界不变量。
- 明确不可接受的后果、可接受的残留与恢复要求。
- 比较现有能力、简单流程、人工修复与自动恢复的成本。
- 限定当前故障范围，只记录所选机制依赖的假设。
- 让每个机制回指一项不变量或活性目标。

## Verification

- 验证正常流程及最大真实风险，核对不变量和外部结果。
- 采用人工修复时，验证残留可发现、补做可重试、结果可回读。
- 承诺自动恢复时，对必要故障窗口注入失败，核对最终状态和恢复时限。
- 只有所选机制与当前承诺涉及分区、旧 owner、时钟、版本混跑或状态重建时，展开对应验证。
