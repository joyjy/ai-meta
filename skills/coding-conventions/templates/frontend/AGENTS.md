# 前端工程约定

## Engineering

- 优先沿用项目已有框架、路由、状态管理、请求封装、样式方案和组件系统；不要为了单个需求引入新的前端架构或设计体系。
- 修改局部布局或样式前，先沿页面、容器、组件骨架到内容元素检查完整布局链，明确尺寸、排列、对齐、溢出和响应式分别由哪一层负责；同一布局决策只保留一个 owner，不用子层覆盖或偶然继承修补父层职责不清的问题。
- 同一业务用例的流程、状态、接口契约和错误解释由所属领域维护；公共组件与通用请求层不承载具体业务分支。页面通过领域的明确入口组合功能，领域不反向依赖页面；沿用项目组织方式，不强制新增目录层级。
- 按稳定职责抽取：组件组织呈现与交互，领域流程编排业务，接口适配处理传输和边界数据。只有复用 React 状态或生命周期逻辑时才抽 Hook，纯计算使用普通函数；不按行数拆文件，不把整页复杂度原样搬进 Hook，不增加仅转发参数的层。
- DRY 针对同一语义、同一变化原因的重复规则；先确认已有 owner。参与者、授权或协议不同的流程允许保留差异，不因字段或界面相似就合并成万能组件或跨仓共享包。
- 每份状态有一个权威来源；可推导值不另存 state，不用 effect 镜像 props。区分未知、加载中、失败和明确业务值，不能把获取失败默认成否或空结果。简单表单保持简单；出现互斥阶段或多步协商时再显式表达合法转换。
- 提交的异步责任贯穿回调链：返回并等待实际操作的 Promise，pending 覆盖操作周期，同一操作有一个状态 owner；用原生 disabled 语义与提交入口 guard 防止重复触发。明确失败与结果未知分别处理，不把超时一律解释为可安全重试；可编辑输入和错误反馈保留恢复路径。
- API 数据转换集中在所属领域的接口边界，业务判断使用明确契约；前端展示与校验不能替代服务端权限、能力和业务规则，也不能用类型断言或静默 fallback 掩盖契约不明。
- 涉及异步提交、连续输入、乱序响应、后台同步、乐观更新或 Undo 时，读取 coding-conventions 的 `ui-interaction` pattern，按实际风险选择适用机制；纯布局、文案和普通导航不触发完整交互协调流程。
- 可访问性按项目门槛处理；至少避免不可聚焦、无文本替代、键盘不可达和颜色对比明显不足的基础问题。

## Verification

- 对照本次用例检查职责、依赖方向、重复规则与状态来源；重构应减少理解所需的概念或分支，不能只增加文件。局部变更不借机重写无关页面。
- 验证真实业务交互的主路径与最大失败风险，包括适用的配置加载失败、多阶段提交、结果未知和键盘重复触发；helper 单测不能替代调用链与交互验证，不为排列组合或实现细节堆测试。

- 涉及 UI 的改动，完成前必须在浏览器里实际打开页面并走一遍关键交互；不要只靠代码阅读或截图判断完成。
- 同时检查桌面和移动视口，确认没有文本溢出、控件重叠、主画面空白、布局跳动或不可点击区域。
- 若项目已有 Playwright、Storybook、视觉回归或组件测试流程，优先使用项目流程；没有时至少完成手动浏览器检查。
- 前后端分离项目的 agent 本地集成验证，优先用 `npm run build` 生成静态产物再通过 nginx 或简单静态服务器 serve；如果 compose 只需要验证 UI 静态产物和后端 proxy，优先 mount `dist` + `nginx.conf`，不要默认升级为 multi-stage UI image。只有明确要验证 Dockerfile、镜像构建或发布镜像一致性时，才默认走镜像级验收。
