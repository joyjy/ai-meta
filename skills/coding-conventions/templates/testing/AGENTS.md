# 测试策略约定

## Load Order

- 写测试或修改测试前，先读取项目内最接近的测试说明：`TESTING.md`、`docs/testing.md`、`test/README.md`、`tests/README.md` 或测试目录同级说明；若不存在，再按本模板决策。
- 项目测试说明优先记录框架、fixture、数据准备、外部依赖、命名和运行命令；本模板只保留跨项目的测试取舍。

## Terminology

- 测试语境优先直接使用英文术语 fixture、stub 和 mock；不要翻译成“夹具”“桩”或“模拟对象”。

## Layering

- 测试按“提供哪类信心”选择层级，不按单元测试或端到端测试的名义价值排序。
- 单元测试用于隔离复杂、稳定、可穷举的逻辑风险；不为简单转发、薄 wrapper、字段搬运、私有 helper、mock wiring、格式细节或覆盖率数字铺测试。
- 集成 / 端到端测试用于证明真实 workflow 和跨边界契约没有断；优先覆盖用户可感知主路径、跨模块契约、高风险写操作、关键失败路径和历史 wiring 回归。
- 面向 agent 的本地集成验证优先追求稳定、可复现、接近验收面的环境，不默认追求人类在线开发的热更新效率；若静态 build + serve 足以证明跨边界契约，优先选择它而不是更重的发布镜像链路。
- 高风险写操作至少要有一个集成或端到端主路径覆盖；难以构造的边界再用少量单元测试补足。

## Bloat Gate

- 新增测试必须能归类为 workflow 信心、跨模块契约、复杂逻辑隔离、高风险写操作或真实事故回归之一；不能归类的测试默认不加。
- 测试基础设施默认不再铺测试。只有其错误可能静默造成假绿、污染真实环境或触发高风险副作用，且包含非平凡的状态、补偿或契约判断时，才增加一层测试；若错误只会让测试显式失败，默认通过运行真实用例验证，不继续递归测试。
- 修改既有测试文件时，顺手检查低价值断言、过时入口断言、重复 fixture、非主路径边界断言和绑定实现细节的 case；能删则删或合并。
- 修 bug 优先复现：能写测试就先写失败测试；不能写测试时，也要说明用什么命令或手动步骤验证。

## Smoke / Golden

- 当项目缺少 smoke、golden 或主路径回归入口，而当前改动影响真实 workflow、CLI、API 或跨模块行为时，强烈建议用户同意创建最小入口；写入前按项目约定确认范围和位置。

## Pitfalls

- 不要用 `lenient()` 或全局 lenient strictness 掩盖多余 stub；优先删除无效 stub，只在确有条件分支需要时用注释说明例外。
- 核心业务规则、状态流转、计算逻辑和错误分支要有有效断言；不要用简单 API 透传测试掩盖核心逻辑缺口。
