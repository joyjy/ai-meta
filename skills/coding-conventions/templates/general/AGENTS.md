# 通用工程约定

## Load Order

- 开始实现、评审或验证前，先读当前 repo 最近的 `AGENTS.md` / `CLAUDE.md` / README / CONTRIBUTING；项目规则优先于本模板。
- 本模板只保留跨项目工程底线；测试、Git、语言、CLI、前端等细节读取对应模板或项目文档。

## Scope Control

- 贴近当前 scope 和项目既有模式；避免无依据的过度设计、过度抽象、过度兼容、过度防御和过度测试。
- 优先使用语言、平台和项目已有能力；引入新依赖、框架、配置入口或兼容层前，先确认真实使用方和维护成本。

## Risk Checks

- 涉及 API、鉴权、权限边界、输入输出契约、错误响应或日志变更时，主动检查安全边界、敏感信息泄露和兼容影响；具体规则以项目文档为准。
- 涉及并发、异步、跨线程状态或竞态修复时，主动提醒按成熟并发最佳实践设计和验证；不要把时序假设当作事实。

## 日志

- 日志检查覆盖改动涉及的业务路径，不只检查新增 log 语句；已有统一边界覆盖时不补重复日志。范围内的既有日志问题随改动修正，不扩为全仓扫描或日志基础设施重构。
- 新增或调整业务用例、任务或消息处理时，先确认终态日志的责任边界；记录动作、关联标识、结果、必要原因及耗时，覆盖成功、失败、跳过与取消，不依赖开发者在每个 return 前手写出口日志。优先复用项目现有设施，不为满足约定新增通用日志框架。
- 业务代码记录重要状态变化与业务事实；长任务、批处理及重要异步操作补充开始事件。普通内部方法不逐层打印进出日志；受理、入队和实际完成分别表达，不能互相替代。
- 同一失败的完整堆栈由明确的异常处理边界记录一次；内部层补充必要上下文或传播异常，不层层重复打印。正常业务结果用 INFO，诊断细节和常规无操作跳过用 DEBUG，需要关注的阻断或可恢复异常用 WARN，未恢复的执行失败用 ERROR；不把所有拒绝或 4xx 都视为系统错误。
- 使用稳定事件名和结构化字段，通过 request / trace / business 标识关联操作；参数与结果只记录必要摘要，不输出完整对象、密码、Token、验证码或带凭证的链接。日志用于诊断，不替代业务状态、投递回执或要求可靠留存的审计事实。

## Verify

- 完成一个 slice 时，应能说明实际运行过的编译、类型检查、测试、格式化或 lint 命令；未运行时说明原因。
