# 通用工程约定

## Load Order

- 开始实现、评审或验证前，先读当前 repo 最近的 `AGENTS.md` / `CLAUDE.md` / README / CONTRIBUTING；项目规则优先于本模板。
- 本模板只保留跨项目工程底线；测试、Git、语言、CLI、前端等细节读取对应模板或项目文档。

## Scope Control

- 贴近当前 scope 和项目既有模式；避免无依据的过度设计、过度抽象、过度兼容、过度防御和过度测试。
- 先判断是否需要建设，再依次检查项目已有实现、标准库、平台原生能力和已安装依赖。已有方案满足当前验收时停止扩展，只新增缺少的最小行为。引入新依赖、框架、配置入口或兼容层前，确认真实使用方和维护成本。
- 是否增加防御机制，先看异常后果是否违反业务约束或明确验收。异常输入导致的明确失败，如果没有损害安全、数据一致性或已承诺的业务能力，且影响在可接受范围内，可以保留；异常实际发生过，本身不构成新增机制的理由。确需增加时，比较实现、运行、维护与修复成本。当前任务要求的安全校验和防数据丢失处理仍须完成。

## 业务切面检查

- 实现或修复业务行为前，盘点本次业务切面的测试和日志结构。每个可独立验证的行为阶段结束时复核。测试执行 testing 模板，日志执行本文件的日志约定。未计划修改测试或日志时也要检查。纯注释、格式和文档变更不触发。
- 发现有明确收益的局部重构时，在当前任务内完成。重构保持业务契约，复用项目现有设施。收益应指向具体的重复覆盖、准备成本或日志责任缺陷。不要只列建议后结束，也不以新增框架替代局部简化。扩大 scope 或改变契约前请求用户决定。文件删除和外部动作仍遵守授权边界。
- 结束时说明检查范围、结构改动及验证证据。没有合适改动时，说明保留现状的具体原因。不要求每次产生重构，也不设置删减数量指标。

## Risk Checks

- 涉及 API、鉴权、权限边界、输入输出契约、错误响应或日志变更时，主动检查安全边界、敏感信息泄露和兼容影响；具体规则以项目文档为准。
- 涉及并发、跨线程状态或竞态修复时，验证顺序与同步依据，不把时序假设当作事实。
- 新增或改变异步资源时，确认准入、已接收工作和退出预算。区分正常关闭与崩溃恢复；复用已有生命周期能力，不默认新增 drain 框架。
- 改变业务唯一键或软删除时，先明确标识复用与恢复语义。改变时间存储或转换时，先明确时间点、日历时间与时区；具体数据库实现按条件选择。
- 批量修改或清理持久数据时，确认目标范围、执行预算、并发复验和失败后的恢复位置。先查现有索引与事务能力，不预设扫描算法。

## 日志

- 沿本次业务路径检查入口、业务处理、异步交接和异常边界。核对终态日志、完整堆栈和关联上下文的责任归属。识别分散出口、重复摘要、重复堆栈和异步上下文丢失。检查受理、入队与实际完成是否混淆。已有统一边界覆盖时不补重复日志。
- 发现日志责任缺陷时，按已有边界收敛重复记录和分散出口。移除无诊断价值的逐层进出日志，补齐必要的终态和关联上下文。不能只调整日志文案或级别后结束。保持业务契约及项目要求的日志消费契约。不扩为全仓扫描或日志基础设施重构。
- 新增或调整业务用例、任务或消息处理时，先确认终态日志的责任边界；记录动作、关联标识、结果、必要原因及耗时，覆盖成功、失败、跳过与取消，不依赖开发者在每个 return 前手写出口日志。优先复用项目现有设施，不为满足约定新增通用日志框架。
- 业务代码记录重要状态变化与业务事实；长任务、批处理及重要异步操作补充开始事件。普通内部方法不逐层打印进出日志；受理、入队和实际完成分别表达，不能互相替代。
- 同一失败的完整堆栈由明确的异常处理边界记录一次；内部层补充必要上下文或传播异常，不层层重复打印。正常业务结果用 INFO，诊断细节和常规无操作跳过用 DEBUG，需要关注的阻断或可恢复异常用 WARN，未恢复的执行失败用 ERROR；不把所有拒绝或 4xx 都视为系统错误。
- 使用稳定事件名和结构化字段，通过 request / trace / business 标识关联操作；参数与结果只记录必要摘要，不输出完整对象、密码、Token、验证码或带凭证的链接。日志用于诊断，不替代业务状态、投递回执或要求可靠留存的审计事实。

## Verify

- 完成一个 slice 时，应能说明实际运行过的编译、类型检查、测试、格式化或 lint 命令；未运行时说明原因。
