# piggyback

`piggyback` 是执行前的一次性加深。它站在领域高手的肩上看当前请求，把高手默认会做、请求里没写的部分补进请求。目标是更深，不是更大：范围与原请求相同。

## Trigger

- 用户说「巨人的肩膀」或 `piggyback`。
- 在不熟悉的领域开始设计方案、验收方式、上线计划或迁移计划之前。
- 开始写设计稿或研究稿之前。

熟悉代码库里的日常修改、路径明确的修复和纯事实查询，跳过本 skill。已有候选方案要裁决时用 `steelman`。方案有结构性分歧要压测时用 `grill`。同一轮只运行一套。

## 先取证

能从代码、文档、数据和工具查到的现状，先查清。高手做法必须落到当前对象上，不写泛泛的最佳实践。

取证后核对请求是否对题，也就是请求是不是某个上层目标的一种解法。如果证据显示高手为这个上层目标会选别的解法，把这个判断列为「只有用户能答的问题」的第一条阻塞问题。只提问，不自行改写请求的目标。

## 五问

- **高手会做的事**：列出领域高手在这里会做、请求里没写的事。按两类输出：
  - 范围内：换方法、补检查、改验收方式。这一类写进改写后的请求。与用户指定方案冲突的换法按「加深之后」处理。
  - 扩大范围：新功能、新开关、新交付物。这一类在请求外用一行列为提议，不写进请求。
- **一手材料**：高手会从哪份原始材料开始，而不是从已整理的摘要或状态字段开始。写到具体来源，例如哪份规范、哪张表、哪段日志、哪个源码位置。
- **方法和工具**：列出高手会用的具体方法和工具。优先用 `~/.ai/tool-routes.md` 登记的入口和本机已有工具。
- **外部验证**：除了用户和 agent，什么能证明结果正确。例如测试、线上数据、对照基线、规范一致性检查、第三方评审。模型自评和「看起来合理」不算。
- **只有用户能答的问题**：目标、权限、验收取舍和优先级。列成问题，不自行补全。

高手做法、方法和工具写出来源：规范、RFC、厂商文档、项目约定或可查证的工程实践。没有来源时标「推断」，不写成共识。

## 加深之后

- 如果加深没有新增内容，用一句话说明，然后按原请求继续。
- 如果「只有用户能答的问题」中有阻塞项，只问第一条。
- 如果高手做法与用户指定的方案冲突，并且两者都有合理成立条件，这个冲突算阻塞项。输出里加一行「建议换用：`steelman`」。
- 如果「只有用户能答的问题」里有 2 个或更多相互耦合的结构性问题，仍只问第一条，并加一行「建议换用：`grill`」。
- 如果没有阻塞项，并且原请求已授权执行，按改写后的请求继续，不再请求确认。
- 如果原请求没有授权执行，输出改写结果后停止。

「建议换用」只写 skill 名和原因。是否把改写后的请求交给 `final-form` 收成规格，或按「建议换用」切换 skill，由调用方决定。本 skill 不自动转交。

## Boundaries

- 范围与原请求相同。扩大范围的事只列为提议。
- 改写结果不授予新权限。Git、删除和远端写入仍按全局规则执行。

## Output

```markdown
高手会做：...
提议（扩大范围，未写进请求）：...
一手材料：...
方法和工具：...
外部验证：...
需要你回答：...
建议换用：...

改写后的请求：...
```

空行省略。改写后的请求写明目标、一手材料、方法、外部验证和不做的事。简单请求可以合并成一段。
