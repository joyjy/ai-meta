# 变更导读

用短文本解释业务功能与代码职责的对应关系。文件和类用于观察领域边界。跨文件多本身不证明领域泄露。

## 范围

沿用入口绑定的 target 与 baseline，统计同一份 diff。缺少 diff 基线时，先解析基线。禁止用当前文件总行数代替改动行数。

## 输出

导读正文不超过 15 个非空文本行。只请求导读时，不附加 strategy、verdict 或 next-review。完整评审仍按入口格式输出，避免重复导读中的证据。

1. 用一行列出文档、源码、测试的新增／删除行数。配置、生成文件单列，避免重复计数。
2. 按业务功能说明源码变化，每个功能一行。格式为“做了什么 → 主要模块／类及各自职责”。使用简单的业务语言，省略技术分层清单。
3. 用剩余行指出领域泄露迹象。列出具体位置与依据。证据不足时标为待确认。没有明确迹象时，用一句话说明证据范围。

只列足以看清职责边界的模块、文件、类或函数。省略完整文件清单和调用链。优先压缩路径和重复措辞，保留业务功能与实质风险。若仍超出行数预算，说明未展开的范围。

## 领域泄露线索

- 业务规则进入通用层或基础设施层。
- 一个领域直接处理另一个领域的内部规则。
- 同一业务规则散落多处，导致职责归属不清。

根据实际职责、规则归属和依赖方向判断。正常编排、接口适配或跨模块调用本身不证明领域泄露。行数只解释变更构成，不能单独证明过度设计。
