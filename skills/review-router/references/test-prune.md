# 测试减法评审

用于 `rr prune tests <仓库/命令族/测试目录>`、删减测试、最小测试集合或激进测试瘦身请求。strategy 固定为 `prune`。这里只定义测试场景的评审产物，保留标准使用入口直接加载的 testing 模板，不建立第二套准入规则。

## 范围与证据

- 沿用 review-router 的 scope、identity 和 baseline。明确审的是 diff、命令族、目录还是全套测试，不能用最近修改代替完整对象。记录 revision 或工作树指纹及已有改动。
- 盘点范围内所有 case、测试准备代码、helper 和真实进程入口，按业务/命令族关联被测消费者。runner 报告项、显式 case、空测试模块和动态生成用例分别计数。静态计数与估算须标明。
- 读具体断言及相应消费者，核实真实事故、权限/副作用、外部契约的来源。测试名称、独立场景或作者声称的“防回归”不代替证据。逐项裁决。抽样时列出未检查范围，不能声称全套已审完。
- 数量、覆盖率、测试/代码比和进程数采用同 revision、同口径的已有证据。不可用则记未知。只读评审不为填指标运行测试或生成覆盖率。用户另行授权实际测量时使用项目现有命令，不新增诊断框架。

## 从裁决到计划

- 每项记录 `retain`、`delete` 或 `shrink`。保留写明 testing 模板中的价值依据及具体故障后果。删除允许 replacement 为 nothing，写明撤掉的检测能力、可接受风险和仍受保护的边界。有重复覆盖才指出实际保留位置，不虚构替代覆盖。
- 普通与激进评审使用同一标准。激进意味着撤掉不值得维护的检测能力。不以目标 case 数凑删除。不默认保住所有独立场景。不通过打包 case 隐藏成本。高风险证据有缺口时只对该项保留待核实，不把所有未知都升级成必保风险。
- 优先整例删除及闲置 import/helper，其次缩小保留测试的 fixture。只有具体实现能净减时才提共享准备代码或下沉。给出实际替代方式与代码预算，不推荐新通用 fixture 框架或空泛“表驱动优化”。
- 计划列出 exact file/line/case、整文件删除路径、保留覆盖、预计净减行数与进程成本。区分真正删除的业务场景、重复验证减少和仅准备代码缩小。不能把 case 数变化当成检测能力损失的替代指标。

## 结果与执行边界

输出按净减排序的 ponytail 标签行，例如 `<file>:L<line>: delete: <删除项>。replacement: nothing。` 或 `shrink: <原体积与具体替代>。`，并附：

- 命令族总览：当前 case 与成本、拟删除/保留项、关键保留依据。
- 可应用清单：位置、动作、替代、lost detection、accepted risk、行数/进程估算。高风险待核实项单列。
- 汇总：去重后的预计净减及范围，说明计算口径。没有可删项时给出 `Lean already. Ship.`，不强行生成候选。
- `next_review.strategy` 与理由。已能形成具体计划时为 `none`，真实调用方或权限边界未证实时可为 `challenge`，指出 exact 未决问题。

以 `net: -<N> lines possible.` 或明确的估算区间汇总。未应用的估算禁止写成实测。默认只读，不因产出计划获得删除、Git 或远端权限。用户批准后，实现任务执行清单。实现任务核对批准清单、跑适用检查，报告实际净减与检测损失。不因覆盖率下降补回低价值测试。
