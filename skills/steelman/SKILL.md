# steelman

`steelman` 是一次性的有界决策过程。它用于降低过早否定、知识不对称和弱化对方观点造成的误判，不以温和措辞或形式上的平衡为目标。

## Trigger

- 用户明确要求钢人化某个方案、评论或双方观点。
- 多个候选都存在合理成立条件，需要在相同标准下裁决。
- 正在评估 reviewer 或领域专家的意见，且当前存在知识不对称。
- 一个看似奇怪、复杂或错误的设计可能承载未显式写出的兼容、运维、authority 或演进约束。

只在证据基本收集完成、准备站队或行动前运行。能从代码、文档、历史或工具查明的事实先查明；不要用钢人化代替取证。

## Bounded Decision Loop

1. **事实边界**：列出直接证据、决策目标和仍未知但会影响裁决的事实。不要把善意解释、常识或框架假设写成已知事实。
2. **钢人版**：恢复对象最强、自洽、可落地的版本，说明它真正解决的问题、成立条件、最强论据和独到价值。双方钢人化时使用同一组评价标准，不给任一方降低门槛。
3. **挑战**：只攻击钢人版，指出决定性假设、最大真实失败模式，以及 compatibility、authority、成本或恢复边界。不要退回攻击原始表述中的弱点。
4. **裁决分水岭**：指出最可能改变结论的一条直接证据或条件；若当前可查，先查再裁决。
5. **明确裁决**：给出采用、拒绝、合并或暂缓的结论。仅当确实影响决策时区分当前处置与长期理想；不得为了平衡保留已被证据否定的方案。

如果钢人化没有改变结论、适用边界或验证要求，简短说明后结束，不展开仪式化长文。

## Boundaries

- 不对时间、路径、运行状态、测试结果或其他机械事实做钢人化。
- 不为已经被直接证据否定的事实续命；可以解释当时决策为何合理，但不能改写当前事实。
- 不把它变成连续追问。用户明确要求持续压测时由 `grill` 拥有对话，不并行运行两套循环。
- 不把钢人结论当成实现授权。只有用户请求本身已经授权执行，且正常 scope 与安全门禁满足时，才能继续修改或产生外部副作用。

## Output

按任务复杂度使用最小必要结构：

```markdown
事实边界：...

钢人版：...

挑战：...

裁决分水岭：...

结论：...
```

简单问题可以合并段落；双方比较时分别呈现钢人版，再共享同一个挑战标准和最终裁决。
