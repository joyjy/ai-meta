# 版本检查

项目发布规则决定是否升级版本、升级幅度和执行时点。每个受影响的发布单元单独判断。构建工具或依赖版本的变化本身不足以证明交付必须升级版本。

1. 根据变更范围识别受影响的发布单元。包括独立发布的服务、包或插件。
2. 核对项目发布规则和发布配置。按「版本评估基线」绑定基线版本及对应源码或产物。
3. 比较基线与拟发布内容，判断是否必须升级版本。适用时，按「语义化版本」判定升级级别。
4. 核对拟发布版本是否满足判定。核对权威声明及项目要求同步的版本字段、产物或发布坐标。如果项目在合并后定版，核对定版入口并记录负责方和触发条件。

## 版本评估基线

服务以目标生产环境实际部署的版本为基线。用部署记录或线上产物标识绑定版本和源码 revision。独立分发的包或插件以目标渠道的已发布版本为基线，用发布记录绑定版本和源码 revision。

评估范围是基线到拟发布产物的全部变化。已经合入但尚未发布的变化，只要会随产物一起发布，就计入评估。代码评审仍按原定评审基线核对本次变更。

例如线上为 `1.2.3`，目标分支已有未发布的新功能。即使本次只修复缺陷，只要两项一起发布，仍需 `minor`。如果拟发布版本已定为 `1.3.0`，该版本满足级别要求。

首次发布时，记录尚无已发布版本的证据。初始版本按项目发布规则确定。如果已有线上版本但无法核实，记录证据不足。禁止用默认分支、合并请求目标分支或未经发布记录验证的标签代替。

## 语义化版本（SemVer）

以项目承诺支持的公开契约为准。公开契约可以包括接口、命令行、配置、数据格式和行为。比较基线和交付版本，确认原有用法是否仍符合这些承诺。

| 级别 | 判定条件 |
| --- | --- |
| `major` | 原有受支持的用法不再兼容。例如移除公开接口，或修改默认行为并违反既有承诺。 |
| `minor` | 新增向后兼容的公开功能，或将公开功能标记为弃用。保留原有用法的可选参数属于这一档。 |
| `patch` | 向后兼容地修复缺陷。例如恢复既有契约规定的行为。 |

同一发布单元含多类变更时，取最高的必需级别。仅有文档、测试或内部调整时，按项目发布规则判断。SemVer 允许重大内部改进采用 `minor`。升级 `major` 时将 `minor` 和 `patch` 归零。升级 `minor` 时将 `patch` 归零。

对 `0.x`，记录实际兼容性影响，再按项目规则确定升级级别。缺少项目规则时，记录证据不足。依据见 [SemVer 2.0.0 第 4 至 8 条](https://semver.org/#spec-item-4)。

## 检查结果

每个发布单元记录环境或渠道、基线版本及其证据。记录预期级别、拟发布版本和结论。适用 SemVer 时，指出决定级别的具体契约或修复。记录满足要求、版本缺失或错误、合并后定版、不适用、证据不足中的一项。

如果没有受影响的发布单元，记录不适用及原因。如果无法确定版本来源或升级规则，记录缺少的证据。
